# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 35-37) | Checked `minutes > 10` after integer floor division. A punch-in at `09:40:01` on a `09:30` shift is 10.016 minutes late (> 10:00 grace), but `int(...)` truncated to 10, so `10 > 10` evaluated to False and returned 0. Also failed to handle overnight shifts and timezones. | Input punch at `09:40:01` returned `late_minutes = 0` instead of `10`. | Checked elapsed seconds strictly `> 600` before whole-minute floor division (`elapsed_seconds // 60`). Added timezone conversion and overnight shift alignment. |
| 2 | `compute_work_hours` (lines 40-41) | Used Python built-in `round()`, which applies banker's rounding (round half to even) and float inaccuracy. Rule R4 mandates exact half-up rounding (`ROUND_HALF_UP`) to 2 decimal places. | Inputs with midpoint values (e.g. `2.125`) rounded down to `2.12` instead of up to `2.13`. | Replaced with `(Decimal(diff_sec) / Decimal(3600)).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`. |
| 3 | `compute_overtime` (lines 44-47) | Awarded overtime for any positive difference (`max(0, ...)`). Rule R3 requires overtime to be counted only if $\ge$ 30 minutes; otherwise 0. Also failed to shift `shift_end` to the next calendar day for overnight shifts (`shift_end <= shift_start`). | Punch-out 15 minutes after shift end returned `overtime_minutes = 15` instead of `0`. | Computed `diff_minutes = elapsed_seconds // 60`, returning it only if `diff_minutes >= 30` else 0. Added +1 calendar day to `shift_end` for overnight shifts. |
| 4 | `GET /health` (lines 72-74) | Returned `{"status": "ok"}` statically without checking database health. Contract specifies 200 only when MongoDB answers a ping; else 503. | Stopping MongoDB still resulted in a 200 OK response from `/health`. | Pinged database with `client.admin.command("ping")` wrapped in `try/except`; raised `HTTPException(503)` if unreachable. |
| 5 | `POST /employees` (lines 79-80) | Race condition: checked `find_one` followed by `insert_one` without a database unique constraint. Two concurrent requests with the same `emp_code` could both insert successfully. | Firing concurrent POST requests with the same `emp_code` produced duplicate records or 500 errors. | Created a unique index on `emp_code` at startup and handled `DuplicateKeyError` by raising HTTP 409. |
| 6 | `POST /employees` (lines 53-61, 78) | Allowed identical `shift_start` and `shift_end` (contract states `shift_start must differ from shift_end`). Also lacked regex validations for `emp_code` (`^EMP\d{4,6}$`) and email. | POST with `shift_start: "09:30"` and `shift_end: "09:30"` returned 201 instead of 422. | Added Pydantic field validators and a model validator ensuring `shift_start != shift_end`. |
| 7 | `POST /employees` (lines 82-85) | Stored `datetime.now()` (naive local time) and returned datetime objects directly in response, violating OpenAPI schema requiring integer `EpochMillis`. | Response returned ISO date strings instead of epoch milliseconds. | Stored UTC datetimes in MongoDB and serialized to integer epoch milliseconds in API response. |
| 8 | `GET /employees` (line 93) | Off-by-one pagination skip calculation: `skip = page * page_size`. For page 1, it skipped the first 20 records (showing page 2). | Requesting `page=1` skipped the first 20 employees. | Corrected skip formula to `skip = (page - 1) * page_size`. |
| 9 | `GET /employees` (line 94) | Total calculation `total = db.employees.count_documents({})` ignored the `department` filter. Rule R10 requires `total` to reflect active filters. | Querying `GET /employees?department=Sales` returned total count of the entire collection. | Passed query filter `q` to `db.employees.count_documents(q)`. |
| 10 | `GET /employees` (line 95) | Missing sorting. OpenAPI contract requires employees to be sorted by `emp_code` ascending. | Returned documents in natural insertion order. | Added `.sort("emp_code", 1)` to the query cursor. |
| 11 | `POST /attendance/punch-in` (lines 101, 113) | Crash on unknown employee: queried `emp = db.employees.find_one(...)` without checking if `emp` is None. Accessing `emp["shift_start"]` raised an unhandled `TypeError` (500). | Punch-in with non-existent `emp_code` resulted in HTTP 500 instead of 404. | Added `if not emp: raise HTTPException(404, "Employee not found")`. |
| 12 | `POST /attendance/punch-in` (lines 102-105) | Race condition: checked `find_one` then `insert_one` for duplicate date. Concurrent punches both succeeded. Also, naive `ts.date().isoformat()` violated R1 for overnight shifts (punches before morning `shift_end` belong to yesterday's shift). | Concurrent duplicate punches succeeded; overnight shift punches before `shift_end` recorded the wrong date. | Created compound unique index on `(emp_code, date)` and caught `DuplicateKeyError` as 409. Added overnight shift date calculation per R1. |
| 13 | `POST /attendance/punch-in` (lines 119-121) | Schema violation: returned `"id": str(res.inserted_id)`. Attendance records have no id and `_id` must never be exposed. Datetimes were not serialized to epoch milliseconds. | Response contained extraneous `"id"` field and unformatted datetime types. | Formatted document with `format_attendance_doc`, omitting `_id`/`id` and converting datetimes to epoch milliseconds. |
| 14 | `GET /attendance` (lines 144-147) | Scalability defect: fetched all records into Python memory with `list(...)` and sorted in Python. Also lacked date range validation (`date_from > date_to`). | Crashed / timed out on ~100k records; `date_from > date_to` returned 200 instead of 422. | Added validation `if date_from > date_to: raise HTTPException(422)`. Delegated sorting, skipping, and limiting to MongoDB: `.sort([("date", -1), ("emp_code", 1)]).skip(...).limit(...)`. |

### What was examined and decided was NOT a defect:
- **Synchronous PyMongo client:** Using synchronous PyMongo instead of Motor is fine because FastAPI automatically runs standard synchronous endpoint functions inside AnyIO worker threadpools without blocking the async event loop.
- **Default shift timings `09:30` and `18:30`:** These match the defaults specified in the OpenAPI contract.
- **`date` and `joined_on` stored as strings (`YYYY-MM-DD`):** As explained in `DATA_MODEL.md`, calendar dates are intentionally stored as strings to avoid imposing an artificial time zone on date values.
